# TSConstructor2 · P1 + P2 开发任务：结构感知编辑与跨样本迁移

## 0. 任务目标

请直接在现有 TSConstructor2 项目上进行增量开发，实现：

- **P1：结构识别与定位**——自动检测一条时序中可编辑的几何结构，使用户能够直接选择平台、峰、谷、斜坡等结构，而不必总是手工划定坐标区间。
- **P2：结构锚定与跨样本迁移**——允许配方步骤绑定到一个结构描述，而不只是绑定到某个样本中的绝对坐标；在换用其他基源时，系统重新定位相应结构，并将同一编辑意图应用于匹配到的结构。

核心目标不是增加几个结构检测按钮，而是把系统现有的“坐标 + 参数”式编辑，扩展为“结构目标 + 编辑意图 + 可验证的跨样本匹配”。

本轮开发以 Wafer 数据集的实际可用性为首要目标，同时保持检测引擎尽可能通用。不得为了通过 Wafer 示例而把检测定义硬编码成只适用于某一条 Wafer 样本。

## 1. 现有系统必须继承，不要重写

开工前先检查真实仓库及代码，确认当前分支、依赖、测试、数据文件和实际实现。

根据现有系统文档，重点关注以下模块：

- `src/components/EditCanvas.vue`：编辑画布、选区、点拖拽、波形分层与克隆落点。
- `src/components/ComponentPalette.vue`：组件、编辑和素材方法入口。
- `src/components/RecipePanel.vue`：配方步骤、参数、执行顺序、源和作用域。
- `src/components/VariationPanel.vue`：基源替换、参数扰动、位置、宽度及残差变化。
- `src/components/GenerateBar.vue`：批量生成和批次信息。
- `src/components/ReferenceRack.vue`：基源、片段、纹理供体的角色管理。
- `src/store.js`：会话状态、工作模板、配方及批量实例化。
- `src/engine/recipe.js`：组件形状、操作执行、配方实例化与差异签名。
- `src/components/StructureSurface.vue`：已有 PCA、t-SNE、UMAP 结构面。

以上文件名来自当前系统文档。必须以仓库中实际存在的实现为准。若文件名、职责或状态结构已有变化，请先查清再修改。

### 1.1 保持现有能力

必须尽可能保留：

- 当前的基源 / 片段 / 纹理素材角色。
- 手动框选与点拖拽编辑。
- 脉冲、阶跃、平台、趋势、震荡和噪声组件。
- 时间形变、区间擦除、缩放、克隆和纹理注入。
- 有序配方执行、操作启停、复制、删除与撤销。
- 多基源批量生成及种子化随机机制。
- 当前数据集导入、目标类别和导出契约。

本轮不是代码大迁移。不要因为加入结构感知功能而重写整套状态管理、布局或数据格式。

### 1.2 本轮明确不做

不得顺手加入以下功能：

- 通用因果图编辑器。
- 任意数学函数建模器。
- 自动发现新类别或自动为样本赋予目标语义。
- LLM 自然语言生成规则。
- 复杂的深度生成模型。
- 全新的医学识别引擎。
- 完整候选质量评价与裁决系统。
- 大规模新增组件库。
- 与 P1、P2 没有明确关系的 UI 装饰或重构。

本轮研究范围只有：结构能否被识别、结构能否被用作编辑对象、结构锚定的编辑能否迁移到不同基源。

# P1：结构识别与定位

## 2. P1 的目标与边界

当前操作主要通过绝对采样点、手工选区、固定锚点和宽度定义目标区域。

P1 要增加一种新的编辑入口：

**用户可以在工作波形上看到系统检测到的结构，选择其中一个结构，将它设为编辑目标，并将现有编辑操作绑定到该结构。**

P1 只负责识别和显示可编辑的几何结构，不负责判断某结构在领域中代表什么，也不自动判定它是否属于目标类别。

例如：

- 识别某条波形中可能存在的平台；
- 识别局部峰和谷；
- 识别持续上升或下降的斜坡；
- 显示每个检测结果的边界和基本形态属性。

不得把平台自动称为正常段、故障平台或某个医学成分；不得因为峰高就自动判定其具有某种领域含义。

## 3. 建立独立、纯函数式的结构识别引擎

新增或扩展结构识别引擎，建议使用独立文件：

- `src/engine/structures.js`
- 如确有必要，再建立 `src/engine/structureMatching.js`

应沿用当前项目的 JavaScript 或 TypeScript 代码规范，不要为了这两个阶段引入大型信号处理框架。

结构识别核心应当尽可能是纯函数：

`detectStructures(values, config) -> StructureDetectionResult`

同样的输入波形和配置应产生相同的检测结果。结构识别不得使用 RNG，不得依赖 UI 当前滚动位置或组件内部的临时状态。

### 3.1 统一的结构实例契约

每个识别出的结构实例至少应包含：

- `id`：在当前波形版本及检测结果中稳定的实例标识。
- `type`：结构类型。
- `startIndex`：结构起点，闭区间语义。
- `endIndex`：结构终点，闭区间语义。
- `centerIndex`：代表性中心位置。
- `relativePosition`：中心位置相对于整条波形的位置，范围归一化到 `[0, 1]`。
- `width`：持续样点数或结构宽度。
- `normalizedWidth`：相对于样本长度的宽度。
- `height` 或 `level`：该结构相关的高度、电平或幅度读数。
- `prominence`：适用结构的显著性读数；不适用时明确标记，而不是伪造数值。
- `properties`：各结构额外的、定义明确的属性。

允许使用其他合理字段，但所有字段必须有清楚的定义。

索引范围、空集语义、边界条件以及指标的计算口径必须在代码或文档中说明。

结构实例 ID 不应被当作跨样本的永久身份。跨样本匹配应依据实例的结构描述和测量特征，而不是直接比较两个样本的实例 ID。

### 3.2 第一批只实现三种结构

先实现：

1. 平台 `plateau`
2. 峰与谷 `peak / valley`
3. 斜坡 `ramp`

**不要首版同时扩展阶跃、脉冲、周期模式、复杂波形分段等其他类型。**

原因是本轮要先验证结构锚定机制本身是否有价值，而不是追求检测器类型数量。

现有组件 `pulse`、`step` 等可以继续使用，但不意味着检测器必须将每个现有组件类型都转化成已检测的结构。

### 3.3 平台检测

平台检测不能要求数据点完全相等。它应允许存在一定的波动，但需要在连续的一段区间内具有相对平缓的变化。

最低要求：

- 通过局部斜率、区间波动或等价的可解释准则识别平缓区域。
- 允许用户设置最小长度和合理的平缓程度。
- 能将相邻且只被很短间隙分隔的候选区间合并。
- 去除不满足最小宽度的极短检测结果。
- 每个平台输出清晰的起止边界、中心、宽度及代表电平。
- 在用户选择后，显示其边界及相应形态属性。

检测算法和默认参数应根据真实 Wafer 样本进行调试，但参数不能只针对某一个样本硬编码。

### 3.4 峰与谷检测

使用局部极值、最小间距和显著性等可解释规则检测峰与谷。

最低要求：

- 峰与谷的定义互相一致。
- 能控制最小显著性和最小间距，减少噪声产生的大量伪检测。
- 处理重复值、平顶峰、端点峰以及多个相邻候选。
- 当检测到的实例高度重叠时，采用确定性的去重规则。
- 返回中心位置、幅度、电平、显著性及适用的邻域边界。
- 没有检测到合格结构时，返回空结果并说明原因。

不能保证每个局部极大值都具有领域语义，也不能将几何检测结果自动标记为故障特征。

### 3.5 斜坡检测

识别在一段时间内主要持续上升或下降的区间。

最低要求：

- 使用明确的斜率与持续长度条件。
- 允许有限的小幅局部波动。
- 明确区分持续斜坡与单个短暂跳变。
- 处理斜坡被噪声打断和多个斜坡相邻的情况。
- 返回起止边界、方向、拟合斜率、总变化幅度及宽度。

斜坡检测只描述局部几何趋势，不能据此判断其物理原因。

### 3.6 阈值和检测敏感性

不同数据集的幅度尺度可能不同，不要直接把某个原始数值作为适用所有数据集的固定阈值。

优先采用有清楚意义的局部或样本归一化属性，例如相对于样本尺度的幅度、相对持续长度或归一化位置。

如果需要可配置阈值：

- 设置合理且有限的默认值。
- 暴露少量直观的检测敏感性设置。
- 将详细阈值放到折叠的高级设置中。
- 明确区分原始值、归一化值及其单位。
- 不得在系统没有显示的情况下静默改变判定阈值。

第一版不需要让用户为每种结构编辑十几个参数。

## 4. P1 的界面要求

### 4.1 编辑画布中的结构叠加

在 `EditCanvas` 或现有编辑画布中加入可开关的结构检测叠加层。

结构叠加应与以下已有元素共存：

- 基源波形。
- 当前工作模板。
- 已有选区。
- 中间配方结果及最终结果。
- 当前直接编辑的预览。

视觉设计要求：

- 不同结构类型可以用清晰且可区分的标记样式。
- 平台和斜坡使用带边界的区间标记。
- 峰和谷使用位于实际索引处的标记。
- 选中结构时，边界和属性应明显突出。
- 不得让结构标记覆盖波形本身。
- 提供独立的显示 / 隐藏开关。
- 显示当前使用的检测配置或敏感性状态。

不要同时把所有检测标签一直显示在画布上。应允许按类型过滤，避免标记过多而无法阅读。

### 4.2 结构列表或结构选择器

提供一个紧凑的结构列表。可以按照类型、位置和实例索引展示，例如：

- 平台 1：位置 0.18，宽度 14。
- 平台 2：位置 0.43，宽度 21。
- 峰 3：位置 0.66，显著性 1.2 个归一化尺度。
- 斜坡 2：位置 0.72–0.88，方向为下降。

这里只是显示示例。实际读数必须来自检测结果，不能伪造。

点击列表中的结构时，应同步：

1. 高亮波形上的对应结构。
2. 显示结构属性。
3. 将它设置为当前选中的结构对象。

当检测结果为空时，显示明确的空状态，不显示虚构的结构。

### 4.3 交互行为

必须支持：

- 显示 / 隐藏结构叠加。
- 按结构类型筛选。
- 从结构列表选择结构。
- 直接点击波形标记选择对应结构。
- 查看结构的起止位置和属性。
- 清晰地知道当前选择的是手工选区还是检测到的结构。

P1 不要求自动编辑结构，也不要求自动生成新类别。

但 P1 的结构选择结果必须可以被 P2 使用；不要单独实现一个只能显示结构、无法绑定编辑操作的可视化模块。

# P2：结构锚定与跨样本迁移

## 5. P2 的核心目标

将当前配方中纯坐标式的操作扩展为结构锚定操作。

例如，用户不再只定义：

“在第 110–130 个采样点缩短这个区间。”

而是可以定义：

“缩短这条波形中靠近尾部、符合指定描述的平台。”

迁移到其他基源时，系统重新检测对应结构，寻找匹配的实例，将同一个编辑意图应用于新结构的位置。

**关键约束：结构锚定只是确定操作对象，不自动决定如何修改结构，也不自动判断候选是否符合目标类别。**

## 6. 兼容现有配方，不要粗暴迁移旧格式

当前配方步骤可能包含 `anchor`、`width`、`span`、`dstStart`、`dstSpan` 等绝对坐标或区间参数。

必须向现有配方步骤增加可选的结构锚定信息，同时保留旧步骤的行为。

建议的概念结构如下，实际字段名可根据仓库现有数据模型调整：

```js
{
  // 现有操作字段继续保留
  type: "warp",
  params: {
    factor: 0.8,
    delta: 0
  },

  // 新增：操作目标
  target: {
    mode: "structure",

    descriptor: {
      type: "plateau",
      relativePosition: 0.78,
      normalizedWidth: 0.16,
      relativeLevel: -0.7,
      context: {
        // 可选：相邻结构或局部趋势描述
      }
    },

    location: "center",
    offset: 0
  }
}
```

以上仅为语义示例，不是必须照抄的 schema。

实际实现要求：

- `mode = absolute`：沿用当前坐标或选区执行方式。
- `mode = structure`：依据结构描述匹配当前基源上的结构。
- 不得在缺少结构匹配时静默回退为旧的绝对坐标。
- 旧配方中没有 `target` 时，应自动沿用原有绝对坐标语义。
- 导出配方和候选时，保留结构锚定定义、匹配结果以及实际执行位置。

结构锚定失败必须明确报告，不能静默忽略这一步后继续把候选当作正常产物。

---

## 7. 结构锚点应该包含什么信息

不要仅用“第几个平台”作为跨样本定位依据。

建议将结构锚点描述为一组可检查属性：

- `type`：平台、峰、谷或斜坡。
- `relativePosition`：在整条波形中的相对位置。
- `normalizedWidth`：相对于样本长度的宽度。
- `relativeLevel`：相对基线或样本尺度的电平。
- `prominence`：适用时的相对显著性。
- `direction`：适用于斜坡的上升或下降方向。
- `context`：可选的前后局部趋势、邻近结构类型等。
- `location`：操作位于匹配结构的开始、中心、结束或指定相对偏移。
- `offset`：相对于所选结构位置的附加偏移。

并非每个结构类型都需要所有属性。

应根据结构类型选择适用特征，不能用峰的显著性去强行评价平台。

锚点描述必须在操作绑定时保存为独立数据，而不是每次打开界面时仅依靠当前结构列表中的实例顺序重新猜测。

## 8. 结构匹配与跨样本迁移

新增纯函数式的匹配接口，例如：

`matchStructure(descriptor, detectedStructures, config) -> MatchResult`

要求：

- 只匹配兼容的结构类型，或者明确允许的类型映射。
- 综合结构位置、宽度、相对电平、方向和上下文等适用特征。
- 统一特征尺度，避免某个特征因数值范围更大而完全主导匹配。
- 提供明确的匹配阈值或拒绝规则。
- 区分匹配成功、多个候选难以区分、没有候选和检测失败。
- 相同输入与配置必须产生相同的结果。
- 记录匹配到的结构实例、匹配得分或距离，以及未匹配原因。

匹配不是类别识别。匹配分数只是候选结构与用户指定锚点描述的相似程度，不得显示成类别正确率或医学置信度。

### 8.1 相对顺序与结构位置

允许使用诸如“尾部区域的低平台”或“中部较宽的平台”等描述，作为结构匹配的额外依据。

也允许提供“该区域内第 k 个平台”这种选择方式，但它只能是结构描述的一部分，不能代替其他特征。

如果两个结构在位置、宽度和上下文上都相似，系统可能无法知道用户最初想要哪一个。遇到这种情况必须显示歧义，允许用户手动确认，而不是假装自动匹配可靠。

### 8.2 匹配失败处理

所有匹配失败都必须显式处理：

- 无候选结构。
- 匹配候选过多或不唯一。
- 目标结构不具备当前操作所需的长度。
- 操作参数在当前结构上不可执行。
- 当前基源的长度或结构与目标描述差异过大。

UI 需要说明问题类型，并提供合理处理方式，例如重新选择锚点、调整描述、排除当前基源或切换回绝对坐标编辑。

禁止将匹配失败静默转换为“按原来的第 110–130 点操作”。

## 9. 将现有操作绑定到检测结构

至少支持以下操作通过结构锚点使用。

### 9.1 局部结构变换

- `warp`：对匹配结构覆盖的区域执行时间形变。
- `scale`：对匹配结构覆盖的区域执行局部缩放。
- `deform`：将形变锚点定位到匹配结构的指定位置。
- 适合局部作用域的现有组件：按用户指定的结构位置作为插入锚点。

这些操作必须复用现有执行函数，除非某个现有执行函数存在明确的 bug 或无法支持结构边界。

例如，“缩短匹配到的平台”应根据匹配平台的实际范围构造本次操作的执行区间，而不是再让用户输入一个新的绝对坐标区间。

### 9.2 在结构相对位置插入组件

支持以下概念：

- 在匹配结构开始处插入震荡。
- 在匹配结构中心添加脉冲。
- 在匹配结构结束后添加阶跃。
- 相对匹配结构向前或向后偏移指定点数后添加组件。

具体示例只是说明能力，不要求增加大量专用按钮。应通过统一的结构定位方式配置现有组件。

### 9.3 保留自由编辑

用户仍然可以手工框选任意区间、手工拖拽和添加普通组件。

手工选区与结构锚点应该是并存的两种作用域模式：

- 绝对区间模式：用户精确指定位置。
- 结构锚定模式：用户指定目标结构及其相对位置。

不要为了推广结构锚定，而强制要求所有操作都经过自动结构检测。

## 10. 跨样本迁移的执行契约

这是 P2 最重要的语义部分。

系统至少要支持如下过程：

1. 用户选择一个源样本。
2. 系统检测出若干结构。
3. 用户选择一个结构，并将某个配方步骤绑定到它。
4. 配方保存结构描述，而不只保存当前位置。
5. 用户选择多个基源进行批量生成。
6. 对每个基源单独执行结构检测。
7. 将锚点描述与该基源的结构实例进行匹配。
8. 在匹配结构上解析这一步操作的实际坐标。
9. 执行当前配方，并在候选中保存实际匹配结果。
10. 将匹配成功和失败分别反馈给用户。

### 10.1 推荐的 v1 执行语义

为了保持确定性，首版建议：

- 结构匹配默认基于每个基源的**未修改原始波形**。
- 配方中结构锚点映射到的实际区间，在当前基源开始执行这批配方前确定。
- 后续配方步骤使用当前管道输出作为操作输入，但结构锚点仍以原始基源的结构位置作为参考。
- 不提供基于前一步生成结构重新检测的动态依赖功能。

这样可以让多步配方的执行顺序和定位语义更清晰，不会因为前一步修改了局部形态，就导致后续步骤无法找到最初的目标结构。

如果原始基源缺少目标结构，当前基源上的该配方步骤应明确失败。其他可执行步骤如何处理应沿用现有执行策略，但候选必须能够报告失败的步骤，不能隐藏部分失败。

### 10.2 结构锚定不是任意曲线生成

不要试图在本轮支持：

- 结构锚定之间的任意依赖。
- 任意循环结构引用。
- 对每一步执行结果自动做语义重解释。
- 将多个结构自动组合为新类别的潜在规则。
- 从波形中自动推断目标类别。

这些都不属于 P1、P2。

---

## 11. 必须新增的跨基源匹配预览

如果不让用户在生成之前查看锚点如何迁移，结构匹配只能成为一个黑箱，这违背本轮目标。

当用户选择多个基源后，提供一个紧凑的匹配预览。

最低要求：

- 显示每个基源及结构匹配状态。
- 允许逐个查看检测到的匹配结构。
- 显示源锚点与目标结构的主要属性对比。
- 允许用户确认、调整目标描述或排除当前基源。
- 匹配失败与歧义都必须可见。
- 匹配预览不得自动更改源数据或配方。

匹配预览应复用已有候选或样本预览机制，不要新建一个占据整个界面的复杂工作区。

如果现有 UI 缺少候选波形查看能力，必须补一个**最小候选画廊**用于本轮验证：至少并列显示源波形、候选波形、实际匹配的结构标记和差异签名。

这个画廊只是为了看见与验证构造结果，不是完整的第二阶段质量裁决系统。不要把本轮扩展到判据板、质量评分、自动排序或接纳 / 拒绝治理。

---

## 12. 候选差异和来源记录

P2 不是要彻底解决所有候选多样性问题，但必须使结构锚定和迁移过程可见。

每个候选至少保留：

- 源样本 ID。
- 原始配方定义。
- 当前使用的结构锚点定义。
- 匹配到的结构实例及其原始位置。
- 解析出的实际执行区间、锚点或落点。
- 实际执行的变换参数。
- 当前随机种子及其他必要的随机状态。
- 每一步的成功或失败状态。
- 如存在变换，保留简明的差异签名。

已有绝对坐标操作的差异签名应继续正常工作。

对结构锚定操作，差异签名还应区分：

- 结构目标一致、执行位置不同。
- 匹配到的结构属性不同。
- 基源更换。
- 变换参数不同。
- 操作步骤失败或被排除。

不要将“匹配到了结构”解释成“候选质量更好”。

同样，结构锚定只帮助操作迁移，它不能保证在同一个基源上批量生成很多高度不同的候选。如果所有候选都来自一个基源且变化范围很小，结果仍然可能相似；这应在 UI 和开发报告中明确说明。

# 13. 状态模型、可复现性和兼容性

必须在正式实现前明确以下状态所有权。

### 13.1 检测配置

结构检测配置必须集中管理，不能让画布、列表和生成引擎分别使用不同的默认参数。

### 13.2 检测缓存

如果引入缓存，应根据波形版本和检测配置区分缓存键。配方编辑后不能错误地沿用旧检测结果。

对每个基源生成候选时，应对该基源的原始数据和当前检测配置执行匹配。缓存只能优化性能，不得改变结果。

### 13.3 配方版本与旧数据兼容

旧配方没有结构锚点时，继续使用当前绝对坐标语义。导入或导出格式需要保持兼容；如果确实必须改动格式，应提供显式迁移逻辑并进行回归测试。

### 13.4 可复现性

同一基源、同一配方、同一结构检测配置和同一生成设置，应得到确定的匹配结果和一致的候选。

结构检测与匹配过程不得依赖随机性。如果某步使用随机参数，随机来源仍由现有种子链控制。

不得因为结构匹配失败而暗中换用另一个随机候选或任意坐标。

---

# 14. 必须完成的测试

不要只通过浏览器目测确认功能存在。请编写结构检测与匹配的单元测试。

## 14.1 P1 检测器测试

平台、峰/谷与斜坡每类至少覆盖以下 6 种情况：

1. 理想的简单结构。
2. 加入小幅噪声的结构。
3. 边界附近的结构。
4. 两个相邻或接近的结构。
5. 低于检测阈值或不满足最小长度的结构。
6. 空输入、常量波形或不含目标结构的输入。

需要明确验证起止位置、索引合法性、去重规则和空集语义。

## 14.2 P2 匹配测试

至少包括：

1. 同一个基源的结构能匹配到自身。
2. 结构发生一定的位置偏移后，匹配仍能找到对应结构。
3. 平台宽度改变后，匹配结果仍能依据描述定位。
4. 同一波形中存在多个相似结构时，匹配算法能显示歧义，而不是随意选择。
5. 基源中没有对应结构时，匹配明确失败。
6. 匹配结果不会因调用顺序或界面刷新而改变。
7. 结构锚定的实际执行区间与画布标记一致。
8. 旧的绝对坐标配方行为不变。
9. 同一随机种子和设置可以复现结构匹配及候选。
10. 存在失败步骤时，导出结果中能找到原因。

## 14.3 真实 Wafer 样本走查

使用实际仓库中的 Wafer 数据，选择不少于 8–12 条形态有所不同的样本进行检查。

不要只用一组看起来最工整的样本。应包含：

- 具有清晰平台或斜坡的样本。
- 平台不明显或斜坡较弱的样本。
- 有多个局部峰谷的样本。
- 形态与锚点初始样本存在一定差异的样本。

记录哪些检测结果合理、哪些不合理、哪些跨样本匹配失败，以及是否需要用户调整结构描述。

这项走查是为了检查 P1、P2 能否在真实数据上支持编辑，不是为了证明 Wafer 上的几何结构具有特定物理意义。

# 15. 验收标准

只有以下条件全部满足，才可声称 P1 + P2 完成。

### P1 验收

- 平台、峰/谷、斜坡识别器可以独立测试。
- 用户可以开关结构叠加，按类型筛选和选择结构。
- 选择结构后，能看到其边界与属性。
- 选中的结构能作为编辑步骤的目标。
- 检测配置与结果一致，切换检测配置后不会显示旧结果。
- 没有目标结构时，界面能明确显示空状态或原因。

### P2 验收

- 至少支持现有的 `warp`、`scale` 或适合的组件操作绑定结构锚点。
- 结构锚点包含结构描述，而不是只存原始绝对位置。
- 配方能迁移到多个基源，并在每个基源上重新匹配结构。
- 匹配预览可展示实际命中的结构与匹配失败情况。
- 无匹配时不静默退化成绝对坐标操作。
- 手动编辑与原有坐标式配方仍然可用。
- 批量生成候选时，结构匹配和每一步的执行结果都能追溯。
- 候选波形在 UI 中可见，不必导出 JSON 后才能知道生成了什么。
- 单元测试通过，旧功能的回归测试通过，真实 Wafer 样本走查完成。

# 16. 开发执行要求

请直接执行开发，不要只输出架构说明或伪代码。

具体顺序：

1. 检查仓库、现有代码、测试和运行脚本，确认当前基线。
2. 明确并记录现有配方步骤的真实数据结构与执行语义。
3. 实现纯函数式结构识别引擎及单元测试。
4. 将检测结果接入结构叠加层和结构选择器。
5. 扩展配方，使现有操作能够保存结构锚点。
6. 实现跨基源匹配与匹配预览。
7. 将结构解析后的坐标接入现有操作执行引擎。
8. 补齐必要的候选波形预览。
9. 运行测试及真实 Wafer 样本走查。
10. 更新系统说明文档，明确哪些结构可检测、哪些匹配情形存在局限。

遇到次要实现细节时，可以作出合理且保守的决定并记录假设；不需要每遇到一个小问题就停下来询问用户。

但如果发现当前数据结构根本无法支持某项功能，必须先检查现有执行路径，再决定如何以最小改动实现，而不是绕过已有系统另写一套独立、无法复用的操作引擎。
