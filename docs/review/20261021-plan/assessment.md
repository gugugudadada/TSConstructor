# P1 + P2 两份方案评估与取舍

> 评估对象：
> - `docs/review/20261021-plan/glm.md`（下称 **GLM**，约 117 行）
> - `docs/review/20261021-plan/gpt.md`（下称 **GPT**，约 674 行）
>
> 评估依据：当前仓库 `src/` 的实际实现，而不是只按两份方案自述判断。

---

## 0. 结论摘要

**总判断：两份方案的“方向”都成立，但 GLM 更适合作为本轮基线；GPT 更详尽，不应整份照做。**

| 维度 | GLM | GPT | 结论 |
|---|---|---|---|
| 与当前仓库贴合 | 较好，但漏了已有 `structures.js` | 一般，漏了已有 `structures.js` / `CandidateViewer` / `SourceCorner` | 都需修正，GLM 更贴近 |
| P1 可行性 | 高 | 高 | 现有检测器可复用 |
| P2 可行性 | 中 | 中 | 匹配与目标解析是主要难点 |
| 研究价值 | 高 | 高 | P2 是核心价值，不是 P1 本身 |
| 完整度 | 框架完整 | 文档更全面、更细 | GPT 在“覆盖面”更完善 |
| 保守性 | 高 | 中偏低 | GLM 明确 P1 兜底，GPT 要求全量完成 |
| 可执行性 | 高 | 中 | GPT 有过量要求与少量语义冲突 |
| 总体建议 | **采用为基线** | **选择性吸收** | **GLM 为主，GPT 补测试/验收** |

一句话：

> **更合理、更保守：GLM。**  
> **更完善、更详细：GPT。**  
> **推荐落地：以 GLM 的骨架为主，吸收 GPT 的测试矩阵、状态所有权和验收清单，同时先修正两者共同忽略的现有实现。**

---

## 1. 先校正一个关键事实：仓库里已经有结构检测引擎

这是评估两份方案时最重要的事实。

当前已有：

```text
src/engine/structures.js
```

它已经包含：

- 峰 / 谷 `detectPeaks` / `detectValleys`
- 脉冲 `detectPulses`
- 阶跃 `detectSteps`
- 平台 `detectPlateaus`
- 斜坡 `detectRamps`
- 注册表 `STRUCTURES`
- 一把全跑 `detectAll`
- 确定性、无 RNG、σ 归一化口径、`DETECTOR_SPEC_VERSION`

当前 `recipe.js` 的 `structureFingerprint()` 已经在用 `detectAll()`。

这意味着：

1. **P1 的“识别引擎”不是从零开始。** 真正缺的是：
   - 统一结构实例适配层；
   - 检测配置的集中状态；
   - 画布叠加与结构列表；
   - 把结构选择接到 P2 的 `target`。
2. **两份方案都说“新增 `src/engine/structures.js`”是不准确的。**
   - GLM：明确写“新增”；
   - GPT：写“新增或扩展”，措辞稍好，但也没有指出已有六个检测器。
3. 如果直接照方案新建一份结构引擎，会制造两套检测口径，破坏现有的结构指纹与未来一致性。

**修正原则：**

> 不新建第二套 `structures.js`；先为现有检测器加统一实例适配层，再补 UI 与匹配器。

## 2. 当前系统对 P1/P2 的其他约束

### 2.1 已有可直接复用的部分

- `CandidateViewer.vue`：阶段②已有候选列表、基源/候选波形、差异签名。
- `SourceCorner.vue`：克隆/纹理的源角窗。
- `transplant`（界面名为“克隆”）：已有源段、落点、混合、接缝语义。
- `store.batches`：本会话所有批次。
- `scripts/wafer-1nn.mjs`：Wafer 端到端测试。
- 配方步骤是**扁平字段**（`anchor/width/span/dstSpan/...`），不是嵌套 `params`。
- `runRecipe()` 的既有语义：失败步骤记录原因、保留前值、继续后续步骤。
- `instantiateSteps()` 负责在生成时按 `vary` 改写步骤。

### 2.2 因此，P2 不能“另写一套执行引擎”

正确接入点应是：

```text
原始基源
  → 结构检测（复用现有）
  → 结构描述匹配
  → 解析为现有步骤需要的 span / anchor / dstSpan
  → 进入现有 runRecipe / applyStep
```

不是：

```text
新写一套结构执行器
```

### 2.3 当前缺失的真实部分

- 没有结构检测配置的 store 单一来源；
- 没有结构叠加层与结构列表；
- 步骤没有 `target` 字段；
- 没有匹配器与匹配预览；
- 没有把结构命中/失败写入候选；
- 没有对应的单元测试 runner。

## 3. 两份方案速览

### 3.1 GLM 的结构

GLM 基本按“最小可验证框架”写：

1. 任务目标与边界；
2. 现有系统必须继承；
3. P1 检测引擎契约；
4. 三类检测器；
5. P1 UI（叠加、列表、选区关系）；
6. P2 `target` schema；
7. 锚点属性、匹配器、失败分类；
8. 操作绑定范围；
9. 跨基源执行契约；
10. 匹配预览 + CandidateViewer 集成；
11. 差异签名；
12. 可复现与兼容；
13. 测试；
14. 验收；
15. 执行顺序与 P1 兜底；
16. 结尾三问。

**特点：短、聚焦、边界清楚、有明确 fallback。**

### 3.2 GPT 的结构

GPT 覆盖面更广，基本把 GLM 的每一节展开，并增加了：

- 更细的 UI 交互要求；
- 更细的检测边界条件；
- 状态模型与缓存；
- 更完整的测试矩阵；
- 更细的验收条件和最终交付清单；
- 对候选画廊的要求。

**特点：详尽、可当需求字典，但篇幅长、重复多、部分要求与当前实现不匹配。**

## 4. 逐维度对比

### 4.1 与当前仓库的贴合度

**GLM：较好。**

- 明确列出 `CandidateViewer.vue`、`SourceCorner.vue`、`store.batches`、`wafer-1nn.mjs`；
- 明确要求保留克隆/纹理、素材三角色、选区机制、失败语义；
- 明确把 `transplant` 落点锚定作为旗舰演示；
- 只有 `structures.js` “新增”这一处明显不准确。

**GPT：一般。**

- 模块清单包含 `StructureSurface.vue`，但没有提 `CandidateViewer.vue`、`SourceCorner.vue`、`structures.js`；
- 说“如果缺少候选波形查看能力，必须补一个最小候选画廊”，但当前已经有 `CandidateViewer`；
- 操作绑定范围主要列 `warp/scale/deform/组件`，没有把当前系统最有代表性的 `transplant`（克隆）落点锚定纳入；
- 使用嵌套 `params` 示例，而当前步骤是扁平字段；虽然说了“可调整”，但增加了实现者误读风险。

**结论：GLM 更贴合当前系统；GPT 需要先做一次“现状对齐”才能执行。**

### 4.2 P1 可行性

**两者都可行，且实际难度低于方案描述。**

因为已有六个检测器，P1 真正需要的是：

- 适配输出为统一结构实例：
  - `startIndex/endIndex` ← `i0/i1`
  - `centerIndex` ← `i`
  - `relativePosition` ← `i / (L-1)`
  - `normalizedWidth` ← `width / L`
  - `height/level/prominence` ← 现有字段
- 检测配置集中管理；
- 结构叠加与列表；
- 结构选择状态；
- 与 P2 的绑定入口。

风险在于：

- 现有检测器原本服务于 `structureFingerprint`，其默认参数与“可编辑结构”目标不完全一致；
- 平顶峰、端点、相邻结构、弱平台会产生歧义；
- 结构列表可能过多，需要过滤和空状态；
- 不能把结构检测结果直接当领域语义。

**结论：P1 可行性高；但必须先承认并复用现有引擎，否则会重复造轮子。**

### 4.3 P2 可行性

P2 是本轮真正的价值点，也是主要风险点。

可行部分：

- 当前步骤最终都需要 `anchor` / `span` / `dstSpan` / `dstStart`；
- 结构匹配结果可以先解析成这些数值，再走现有执行路径；
- `transplant` 已有落点字段，适合作为旗舰；
- `vary` 可以在解析后的坐标上继续漂移；
- 候选和导出已有 `steps/tags/baseId` 等承载位置。

难点：

- **匹配不是身份匹配**：同一结构在不同基源上位置、宽度、形态都可能变化；
- 描述相似时会出现多候选歧义；
- 阈值需要真实 Wafer 样本调，不能只看理想波形；
- 多步配方中，后续步骤是否重新检测必须明确（两份方案都选择“不动态重检测”，这是对的）；
- 必须在 `instantiateSteps` 与 `runRecipe` 之间增加“目标解析”层，同时保持旧配方无 `target` 的行为；
- 失败时不能静默回退绝对坐标；
- 导出必须能追溯“描述 → 命中实例 → 实际区间”。

**结论：P2 中等可行；必须限定 v1 语义，并把失败显式化。**

### 4.4 研究价值

两份方案的价值判断基本一致：

- 单纯 P1 只是“检测 + 显示”，价值有限；
- 真正的研究价值在 P2：
  - 编辑意图从“坐标”提升为“结构目标”；
  - 换基源时仍能复用同一构造规则；
  - 直接对应缺类重建中的跨样本构造问题。

GLM 对价值的表述更集中：

> 结构锚定只回答“操作对象在哪”，不回答“改成什么样”“为什么改”“好不好”。

GPT 也反复强调“匹配不是类别识别”，这点同样正确。

**结论：价值高，但应把 P2 作为核心验证，不要把 P1 的检测数量当作成果。**

### 4.5 完整度

**GPT 更完整**，主要体现在：

- 检测器边界条件写得更细；
- UI 交互和空状态更多；
- 状态所有权、缓存、版本兼容更明确；
- 测试矩阵更全；
- 验收清单更细；
- 最终交付物更明确。

但 GPT 的“完整”有代价：

- 大量重复；
- 部分要求是当前已有的（候选查看器）；
- 部分要求可能把范围撑大（检测敏感性高级区、结构列表 + 画布 + 预览 + 画廊）；
- 没有 P1 兜底方案；
- 语义上有一处冲突（见 4.7）。

**结论：GPT 是更完善的“需求字典”，但不是更完善的最小执行计划。**

### 4.6 保守性

**GLM 明显更保守。**

GLM 的关键保守设计：

- 首版只做三类检测器；
- 明确不新增执行分支，只把结构解析成既有 span/anchor；
- 明确优先保证 P1；P2 可截断并附交接说明；
- 不要求新画廊，直接复用 CandidateViewer；
- 不扩张第二阶段检查/裁决；
- 明确“匹配到了结构 ≠ 候选质量更好”。

GPT 的问题：

- 要求 P1 + P2 全量完成；
- 要求“如果缺少候选查看能力就补最小画廊”，但当前已有；
- 验收要求覆盖多个操作和完整测试；
- 没有“先交 P1、P2 可截断”的降级路径；
- 对实现者的约束更多，但范围也更大。

**结论：GLM 更适合“一次不要把细节铺太大”的要求；GPT 容易把首轮做成半成品大工程。**

### 4.7 需要特别指出的 GPT 语义问题

GPT 在 §6 写：

> 结构锚定失败必须明确报告，不能静默忽略这一步后继续把候选当作正常产物。

但当前系统既有语义是：

> 失败步骤保留前值、记录原因、继续执行后续步骤；候选仍产出，但带失败标记。

GPT 在 §10.1 又说“其他可执行步骤如何处理应沿用现有执行策略，但候选必须能够报告失败的步骤”，与 §6 的措辞不完全一致。

这会让实现者面临两种选择：

1. 失败步仍产出候选（当前语义）；
2. 失败步导致候选被拒绝/不当作正常产物（新语义）。

本轮不应改变既有生成契约。**应明确采用 GLM 的表述：失败步可见、保留前值、继续执行、候选记录失败；不静默回退，也不因此改变“能算就产出”的既有约定。**

### 4.8 两份方案共同的缺口

即使选 GLM，也需要补：

1. **先审计现有 `structures.js`**：不要新建重复引擎。
2. **统一实例适配层**：现有 detectors 的输出字段与方案统一契约不同。
3. **检测配置状态**：store 单一来源；画布/列表/生成共用。
4. **目标解析层的位置**：在 `instantiateSteps` 之后、`runRecipe` 之前，还是解析后再实例化？必须写死。
5. **`vary` 与结构解析的顺序**：
   - 建议：先按基源解析结构 → 再应用 `vary` 的位置/宽度扰动 → 再执行；或明确相反顺序。
   - 两份方案都只说“vary 作用于解析后位置”，但没有给出与 `instantiateSteps` 的精确接线。
6. **失败结果如何写入候选和导出**：需要一个统一字段，不只是 UI 灰线。
7. **测试 runner**：当前没有单元测试框架；需要明确用 Node 内置 `node:test` 还是现有脚本。
8. **P1 只复用三类结构还是沿用现有六类**：建议首版只暴露平台/峰谷/斜坡三类，但底层复用现有 detectors；不要删除脉冲/阶跃检测器，它们仍服务结构指纹。
9. **检测配置与结构指纹的关系**：当前 `structureFingerprint()` 直接使用 `detectAll()` 的固定默认参数。增加可调检测配置时，必须明确：
   - 编辑用检测配置是否影响结构指纹；
   - 若影响，需要升级口径/版本；
   - 若不希望影响，应为指纹保留独立默认配置，不能让 UI 改动悄悄改变历史读数。
10. **target 字段的复制与导出**：`duplicateStep`、候选 steps、导出 JSON 都要保留 `target`；否则会出现“画布上有锚定、导出后只剩坐标”的追溯断链。

## 5. 推荐决策

### 5.1 选择

> **以 GLM 为基线，吸收 GPT 的测试与验收细节；不采用 GPT 的全量范围与冗余画廊要求。**

理由：

- GLM 的框架已经够搭起 P1/P2；
- GLM 更符合“先少做、做可靠、可截断”的要求；
- GLM 明确保留当前系统的克隆/纹理、CandidateViewer、失败语义；
- GPT 的详细测试矩阵和状态/缓存要求可以补进来，但其整体范围过大、与当前实现有偏差。

### 5.2 修订后的执行框架

建议把本轮拆成四个可验收的小阶段：

#### 阶段 A：现状对齐与检测适配

- 审计 `src/engine/structures.js`；
- 为现有 detectors 写统一实例适配器；
- 确认 `DETECTOR_SPEC_VERSION`、σ 口径、determinism；
- 建立一个最小的检测配置对象；
- 不改 UI，先让检测结果可被程序化读取。

#### 阶段 B：P1 最小可用

- 画布结构叠加开关；
- 平台/峰谷/斜坡的标记与类型过滤；
- 紧凑结构列表；
- 结构选择状态；
- 空状态与配置回显；
- 不改配方，不碰 P2。

#### 阶段 C：P2 v1 目标解析

- 给步骤增加可选 `target` 描述；
- 实现 `matchStructure`；
- 在既有 `runRecipe` 前解析成 span/anchor/dstSpan；
- 首版支持：
  - `warp/erase/scale` 区间；
  - `component/deform` 锚点；
  - **`transplant` 落点**（旗舰）；
  - 纹理天然全条，不需要结构目标；
- 失败显式记录，不静默回退；
- 旧配方无 `target` 行为不变。

#### 阶段 D：验证与收口

- 匹配预览（紧凑列表/角窗，不建大工作区）；
- CandidateViewer 补锚定命中/失败标记；
- 导出增加 target/匹配结果；
- P1 单元测试 + 匹配单测 + Wafer 8–12 样本走查；
- 如果 P2 超限：交付完整 P1 + 明确 P2 交接，不硬凹全量。

### 5.3 从 GPT 吸收什么

建议吸收：

- P1 检测器测试的六类边界；
- P2 匹配测试的十类场景；
- 检测配置、缓存、版本兼容的显式说明；
- 导出/候选可追溯字段；
- 最终验收清单中的“旧配方不变”“失败不静默”“同 seed 可复现”。

不建议照搬：

- “必须新建最小候选画廊”（已有 CandidateViewer）；
- “所有操作全量锚定”作为首轮硬验收；
- 过细的 UI 装饰/高级阈值面板；
- 任何改变既有“失败步继续执行、候选仍产出但带标记”语义的表述。

## 6. 最终判定

### 更合理

**GLM。**  
它的边界、最小路径、P1 兜底和与当前系统的对齐都更好，适合直接作为开发骨架。

### 更完善

**GPT。**  
它覆盖面更广、测试和验收更细，但更像“需求字典”，不是最小执行计划；其中还有与当前实现不一致的地方。

### 更保守

**GLM。**  
明确限制首版范围、优先 P1、允许 P2 截断，且不要求重造候选画廊或改变既有生成语义。

### 总建议

> **用 GLM 立项，用 GPT 补验收。**  
> 先把现有 `structures.js` 用起来，做一个最小的 P1；再把结构描述解析成现有步骤坐标，先打通 `transplant` 落点这一条旗舰链路；最后用 Wafer 8–12 条样本验证“是否真的比固定坐标更容易迁移”。  
> 不要在第一轮同时追求检测器数量、完整匹配 UI、所有操作锚定和完整候选审查。
