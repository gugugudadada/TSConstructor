我的判断是：这份 C 阶段复审整体上是合理的，可以作为开发决策依据，但还不适合原封不动地交给 Agent 执行。 它把很多实现层面的歧义考虑得很细，不过有几个地方需要区分：哪些是正确的工程约束，哪些是尚待验证的研究假设，以及哪些设计看似严谨、实际可能引入不必要的复杂度。

结合你当前的 TSConstructor 项目目标，我会这样裁定。

## 一、哪些判断是正确的，应该保留？

1\. 复用已有结构检测器，而不是重写一套

这是最重要的工程决策。既然 `structures.js` 已经存在六类检测器，C 阶段就应该构建适配层，尽量复用已有检测逻辑。如果重新实现一遍，可能导致结构检测、结构指纹和后续匹配使用不同的语义定义。

2\. 先补检测器边界测试

这是真正必要的前置工作。理想波形上能够检测到峰和平台，不代表在噪声、边界、相邻结构和空输入下也能正确工作。锚定迁移依赖检测器输出，因此检测错误会一路传递到批量生成结果。

不必一开始追求完整测试矩阵，但至少要有理想输入、加噪输入、边界输入、相邻结构、阈值附近和空输入这几类测试。

3\. 锚定失败必须显式暴露，而不是悄悄退化成普通编辑

如果用户要求“移植到第二个平台”，系统却因为没有找到平台而偷偷使用默认坐标，用户看到的结果可能仍然合理，但实际执行的操作已经违背用户意图。

将匹配失败作为带原因的步骤级失败，保留之前有效的结果并记录失败，是合理的默认方案。不过，必须明确后续步骤如何处理失败状态，不能让后续操作误把旧值当成新步骤的成功输出。

4\. 让用户看到锚定解析结果和歧义

结构锚定是这轮开发最值得验证的功能。如果界面只展示最终生成的波形，用户无法判断跨基源迁移到底是依靠结构匹配，还是碰巧落在了合理位置。

因此，展示目标结构、解析位置、失败原因和歧义候选是必要的可解释性设计。至少应当能够从结果反查这次编辑究竟落在哪里。

5\. 把锚定迁移作为待证伪的研究假设

这比继续堆叠编辑算子更有研究价值。真正值得研究的不是“又增加了一个平台检测器”，而是：相较于固定坐标编辑，基于结构语义的编辑能否在不同基源之间更可靠地迁移？

复审中要求为后续坐标编辑与锚定编辑对照实验留接口，这个方向是对的。

## 二、六个设计决策中，我认为哪些需要修正？

| 决策                | 我的判断          | 建议                              |
| ----------------- | ------------- | ------------------------------- |
| D1：只解析 `dstStart` | 合理的最小实现       | 保留现有落点长度语义，但记录为 v1 的表达能力限制      |
| D2：使用生成时的检测配置     | 合理，但复现条件不足    | 记录检测配置版本或完整快照                   |
| D3：特征归一化、权重和歧义裕量  | 方向正确，细节不能靠直觉定 | 先固定可解释的距离定义，阈值作为配置；不要声称它已是可靠匹配器 |
| D4：C 阶段提供逐候选 tags | 非常赞同          | 保留；同时记录实际匹配对象与解析结果              |
| D5：漂移发生在解析后       | 合理            | 作为明确的操作语义和回归测试                  |
| D6：匹配失败为步骤级失败     | 有条件赞同         | 保留前值、标记失败；规定失败状态如何向后传播          |

有两个细节尤其值得补充。

### 1. D2 不仅需要记录灵敏度，还需要记录检测器版本

同样的源数据、随机种子和灵敏度，如果后续修改了检测算法，也可能得到不同的结构实例。

因此，至少应该记录：

- 检测器实现版本；
- 检测配置快照；
- 匹配器配置及归一化参数；
- 源样本标识；
- 目标结构描述；
- 最终解析出的实例 ID 和区间。

否则，“同 seed 可复现”这个承诺不完整。随机种子只能固定随机过程，不能固定一个不断变化的检测算法。

### 2. D3 不应把“得分最高”误认为“语义正确”

复审建议使用特征归一化、权重和前两名分差判断歧义，这是合理的工程起点，但分差小不一定意味着语义歧义，分差大也不一定意味着匹配正确。

例如，一个基源中有三个平台，而目标基源中只有两个。即使某个候选在特征距离上明显胜出，也可能不是用户希望编辑的那个平台。

因此建议把匹配器定位为：

- 给出候选结构；
- 展示匹配依据；
- 对不确定情况明确报告；
- 允许失败。

不要把它包装成已经解决了跨样本结构对应问题的通用算法。

## 三、我认为这份复审还漏了三个重要风险

### 风险 A：锚定匹配可能只是在更聪明地定位，而不是产生更好的数据

这是最大的研究风险。

假设用户想把某个样本的第二个平台缩短。固定坐标编辑可能在另一个基源上缩短了错误的区间；结构锚定则找到相应的平台再缩短。

这说明锚定可能提高了操作意图的迁移准确性，但它不自动说明生成样本更有价值、更多样，也不说明下游分类性能一定提升。

所以后续实验应拆成至少两个问题：

1. 定位是否更准确？ 锚定编辑与固定坐标编辑相比，是否更经常命中预先指定的目标结构？
2. 构造结果是否更有用？ 在控制生成数量和其他条件后，锚定编辑是否带来更好的样本多样性、质量或下游任务表现？

第一个问题更直接地检验 C 阶段功能；第二个问题才检验它对整个数据增强任务的贡献。不要因为第一个实验成功，就直接宣称第二个问题也得到证明。

### 风险 B：结构检测正确，不等于跨基源语义对应正确

同样被检测为“平台”的结构，可能在不同样本中承担不同作用。对于 Wafer 这种形状相对规整的数据，结构锚定可能表现不错；但换到结构更复杂或类别内部变化更大的数据，效果可能明显下降。

因此，C 阶段不应只测试最漂亮的成功案例。建议至少覆盖：

- 结构清晰、存在唯一匹配；
- 存在多个相似结构；
- 目标结构缺失；
- 结构宽度或位置明显变化；
- 有噪声干扰的情况。

这不是要求现在解决所有情况，而是让失败边界可见。

### 风险 C：不要过早把结构锚定推广成通用时序编辑框架

你最初提出的研究目标，是减少逐条人工编辑的成本，让编辑操作能迁移到不同基源。结构锚定确实可能成为其中一个重要机制。

但“峰、谷、平台、斜坡”目前仍然只是候选结构词汇。不同数据集中的结构定义、检测难度、语义价值都可能不同。

我建议现在先聚焦一个可检验的主张：

> 对于能够被稳定识别的局部时序结构，将编辑目标从固定时间坐标改为结构描述，是否能提高同类编辑操作跨基源迁移的可靠性？

先验证这个主张，再决定是否需要更多结构类型、复杂匹配器或者多变量结构关系。

## 四、C 阶段应该怎样执行？

我建议将复审意见压缩成以下开发顺序，避免 Agent 一边实现一边扩大范围。

## 1

前置验证：检测器可靠性

检查现有六类检测器的测试覆盖，补足边界测试；确认结构选中与普通选区在视觉上有明确区别。明确结构标记属于基源，而非已经编辑过的模板。

## 2

实现最小锚定迁移链路

只实现 `dstStart` 解析，复用已有编辑引擎。实现可解释匹配、显式歧义、步骤级失败与逐候选结果记录。暂不扩展新的编辑算子。

## 3

完成可观察性与回归测试

展示目标、命中结构、实际区间和失败原因；记录检测器版本及配置快照。确认无锚定目标的旧配方逐位保持原有行为。

## 4

先做小规模证伪实验，再决定 D 阶段范围

比较固定坐标与结构锚定的迁移命中率、歧义率、失败率和操作结果。只有当这些结果表明锚定有实际价值时，才继续投资于更丰富的候选查看器或匹配器优化。

## 五、最终裁定

可以进入 C 阶段，但我建议把它定义为一个最小研究原型，而不是一次完整的系统能力升级。

当前最应该避免的不是功能做得少，而是把工程上看起来完整的结构匹配器误当成研究贡献。六类检测器、特征权重、配置管理和审计记录都是实现基础；真正值得验证的是结构锚定相较于坐标编辑究竟改善了什么，以及这种改善在哪些条件下成立。

因此，复审中的 D1–D6 和测试要求大体可以保留；我额外要求补上检测器版本快照，并将实验目标明确分成“迁移定位是否可靠”与“增强数据是否有用”两层。

如果 C 阶段只能交付一个核心成果，我希望它是：用户指定一次结构化编辑目标，系统能在多个基源上可解释地尝试迁移，明确展示成功、歧义和失败，而且可以通过对照实验验证它是否比固定坐标编辑更可靠。
